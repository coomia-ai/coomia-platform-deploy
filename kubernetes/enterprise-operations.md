# Enterprise Deployment Operations

This runbook is a delivery reference for the isolated `classic-enterprise-api`
workload. It is intentionally procedural: rendering a manifest does not grant
cluster access and none of the commands below run automatically.

The Enterprise UI is assembled from the Core fixed entry manifest plus the
private Enterprise edition manifest and runs as `classic-enterprise-ui` on port
3000. API-only rendering remains valid for preflight, but an external Ingress
requires an immutable `CLASSIC_ENTERPRISE_UI_IMAGE`; the renderer keeps
`/api/copilotkit` on `classic-enterprise-api` and sends `/` to
`classic-enterprise-ui`. Do not modify the existing M2 `getai-tools.com` Ingress
until the UI image, TLS, host, and route checks have passed.

The UI's server-rendered pages use the runtime-only `INTERNAL_API_URL`, set to
`http://classic-enterprise-api:8050` in the same namespace. Browser requests
continue through the same-origin `/api` routes. Without the internal address,
Next server components attempt `localhost:8050` inside the UI container even
when browser API requests work. Verify an authenticated dashboard and project
list after deployment; a working login page alone does not exercise this path.

For a Linux release artifact, build the UI from the assembled source with
`coomia-enterprise/ui/edition/Dockerfile.linux.dist`; it installs the locked
dependencies and runs the Next production build inside `node:22-alpine`, then
copies only the standalone runtime and static assets into the non-root image.
The runtime-only `Dockerfile.dist` is reserved for an already-qualified
standalone output and must not receive a Windows `node_modules` tree.

## Preflight

1. Confirm the Enterprise image is a real immutable RepoDigest and record the
   Core and Enterprise source revisions, lock-file digest, and schema-baseline
   digest in the release evidence.
2. Confirm the target namespace is dedicated to Enterprise and has these
   separately managed resources:
   `classic-enterprise-api-secret`, `classic-enterprise-schema-baseline`, and
   `classic-enterprise-license`. When supplied, the UI image creates a dedicated
   `classic-enterprise-ui` Deployment/Service and NetworkPolicy. The rendered candidate also creates the dedicated
   Enterprise Flink namespace and includes
   `classic-enterprise-api-ingress`, which permits API traffic only from Pods
   in the same namespace. If an external Ingress is authorized, provide its
   controller namespace to the renderer so the policy adds only that namespace
   as an ingress source. Label the Secret and schema baseline with
   `coomia.com/data-scope=enterprise`; the Secret must contain the non-empty
   `DATABASE_URL`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `S3_ACCESS_KEY`,
   `S3_SECRET_KEY`, `DORIS_PASSWORD`, `REDIS_PASSWORD`, `TUGRAPH_PASSWORD`,
   `JWT_SECRET`, and `DELIVERY_REPORT_HMAC_SECRET` keys. The read-only verifier
   checks only labels and key presence and never prints Secret values.
3. Confirm the database, object prefixes, Kafka topics, Flink namespace, and
   License store are distinct from the M2 Core deployment. Pre-provision the
   Flink Operator RBAC/admission policy for the rendered namespace according to
   the cluster security baseline. Capacity and storage class checks must be
   recorded before applying the candidate.
4. Render and inspect the candidate without applying it:

   ```bash
   # Optional, only after the host/TLS/controller namespace change is authorized:
   # CLASSIC_ENTERPRISE_INGRESS_HOST=enterprise.getai-tools.com \
   # CLASSIC_ENTERPRISE_INGRESS_TLS_SECRET=classic-enterprise-tls \
   # CLASSIC_ENTERPRISE_INGRESS_NAMESPACE=ingress-nginx \
   # Load both immutable images from the release catalog generated by
   # the multi-repository release adapter; do not retag or hand-copy images.
   CLASSIC_ENTERPRISE_API_IMAGE=ghcr.io/example/coomia-enterprise@sha256:<digest> \
   CLASSIC_ENTERPRISE_UI_IMAGE=ghcr.io/example/coomia-enterprise-ui@sha256:<digest> \
   CLASSIC_ENTERPRISE_CORE_REVISION=<core-revision> \
   CLASSIC_ENTERPRISE_ENTERPRISE_REVISION=<enterprise-revision> \
   CLASSIC_ENTERPRISE_DEPLOYMENT_REVISION=<deployment-revision> \
   CLASSIC_ENTERPRISE_RELEASE_INPUTS=<64-char-input-digest> \
     bash kubernetes/render-enterprise.sh /tmp/classic-enterprise.yaml
   ```

## Project Credential Prerequisites

The API provisions project-scoped Doris and object-storage identities and stores
their lifecycle records in the dedicated Enterprise Flink namespace. The rendered
`classic-enterprise-project-credentials` Role grants only Secret get/create/update/
delete to `classic-enterprise-api` in the Enterprise API namespace. It grants no
list/watch/patch, other resources or access to another namespace. Kubernetes RBAC
cannot restrict Secret CREATE by resourceNames, so keep unrelated application and
infrastructure Secrets out of this API-owned credential namespace. Flink Operator
and job-runtime permissions remain separately managed prerequisites.

Match the IAM provider to the actual shared object-storage service. The renderer
defaults to RustFS; for an existing MinIO service explicitly set
`CLASSIC_ENTERPRISE_OBJECT_STORAGE_IAM_PROVIDER=minio` when rendering. Only
`minio` and `rustfs` are accepted. This configures the administration protocol; it
does not replace storage or change existing keys.

If a project reports `CREDENTIALS_REQUIRED`, first verify these exact namespace
permissions and the provider. Use the authenticated project credential-status
endpoint for secret-free lifecycle state. After fixing the cause, retry the
normal project `/provision` endpoint and require both `ACTIVE` and a managed,
ready credential generation without pending recovery. Retain failed pending
records for the normal recovery algorithm; do not copy bootstrap administrator
credentials into project bundles or force the project status in the database.

## Snapshot before a change

Save the live API/UI namespace, Deployments, Services, ConfigMap, PVC, Ingress,
and dedicated Flink namespace metadata before the first apply. The repository helper refuses
to overwrite an existing output directory and excludes Secret data:

```bash
CLASSIC_ENTERPRISE_FLINK_NAMESPACE=classic-enterprise-flink \
  bash kubernetes/snapshot-enterprise.sh /var/tmp/classic-enterprise-before
```

Keep the output with the release evidence and do not treat it as a data backup.

After rollout, run the read-only boundary check with the exact release identities.
It validates the Enterprise namespace, selectors, immutable image, License and
schema resources, API/UI NetworkPolicies, and Deployment readiness without
reading Secret data or changing the cluster:

```bash
CLASSIC_ENTERPRISE_API_IMAGE=ghcr.io/example/coomia-enterprise@sha256:<digest> \
CLASSIC_ENTERPRISE_UI_IMAGE=ghcr.io/example/coomia-enterprise-ui@sha256:<digest> \
CLASSIC_ENTERPRISE_CORE_REVISION=<core-revision> \
CLASSIC_ENTERPRISE_ENTERPRISE_REVISION=<enterprise-revision> \
CLASSIC_ENTERPRISE_DEPLOYMENT_REVISION=<deployment-revision> \
CLASSIC_ENTERPRISE_RELEASE_INPUTS=<64-char-input-digest> \
  bash kubernetes/verify-enterprise-isolation.sh
```

The verification helper is read-only. A passing rollout status does not replace
the business workflow, database/object/topic boundary, or domain checks below.
The equivalent explicit commands are:

```bash
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get deployment classic-enterprise-api -o yaml > enterprise-deployment.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get deployment classic-enterprise-ui --ignore-not-found -o yaml > enterprise-ui-deployment.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get service classic-enterprise-api -o yaml > enterprise-service.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get service classic-enterprise-ui --ignore-not-found -o yaml > enterprise-ui-service.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get configmap classic-enterprise-api-config -o yaml > enterprise-config.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get pvc classic-enterprise-license -o yaml > enterprise-license-pvc.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get ingress -o yaml > enterprise-ingress.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get serviceaccount classic-enterprise-api -o yaml > enterprise-serviceaccount.before.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get networkpolicy -o yaml > enterprise-networkpolicies.before.yaml
# Metadata only: never export Secret data into the release evidence.
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get secret classic-enterprise-api-secret \
  -o jsonpath='{.metadata.name}{"\t"}{.metadata.uid}{"\t"}{.metadata.resourceVersion}{"\n"}' \
  > enterprise-api-secret.metadata.before.txt
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get deployment classic-enterprise-api \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="api")].image}{"\n"}' \
  > enterprise-api-image.before.txt
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get deployment classic-enterprise-ui --ignore-not-found \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="ui")].image}{"\n"}' \
  > enterprise-ui-image.before.txt
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" rollout history deployment/classic-enterprise-api \
  > enterprise-rollout-history.before.txt
```

The database and external state require their own tested backup or snapshot
procedure. A Kubernetes YAML snapshot cannot restore modified data.

## Rollout and rollback

Apply only after the authorized environment review, then wait for readiness and
record the rollout revision and image digest:

```bash
kubectl apply -f /tmp/classic-enterprise.yaml
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" rollout status deployment/classic-enterprise-api --timeout=10m
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" rollout history deployment/classic-enterprise-api
```

If the candidate fails its health or business checks, stop traffic to the
Enterprise Service, preserve diagnostics, and roll back the Deployment to the
previous ReplicaSet. Do not downgrade a database that has already been changed:

```bash
CONFIRM_ENTERPRISE_ROLLBACK=YES \
CLASSIC_ENTERPRISE_ROLLBACK_IMAGE=ghcr.io/example/coomia-enterprise@sha256:<old-digest> \
CLASSIC_ENTERPRISE_ROLLBACK_UI_IMAGE=ghcr.io/example/coomia-enterprise-ui@sha256:<old-ui-digest> \
CLASSIC_ENTERPRISE_ROLLBACK_UI_REVISION=<previous-ui-revision> \
CLASSIC_ENTERPRISE_ROLLBACK_CORE_REVISION=<old-core-revision> \
CLASSIC_ENTERPRISE_ROLLBACK_ENTERPRISE_REVISION=<old-enterprise-revision> \
CLASSIC_ENTERPRISE_ROLLBACK_RELEASE_INPUTS=<old-inputs-digest> \
  bash kubernetes/rollback-enterprise.sh <previous-revision>
```

The helper uses its positional revision for the API rollout undo and requires
the separately recorded `CLASSIC_ENTERPRISE_ROLLBACK_UI_REVISION` for the UI.
Deployment revision counters are independent and must never be assumed equal. It waits for
readiness and verifies both immutable images plus all recorded release identity
labels/annotations. It refuses
reserved namespaces, mutable image tags, zero digests, missing identity, or a
rollback without the explicit confirmation variable. The equivalent explicit
commands are:
```bash
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get deployment classic-enterprise-api \
  -o jsonpath='{.spec.template.metadata.labels.coomia\.com/core-revision}{"\t"}{.spec.template.metadata.labels.coomia\.com/enterprise-revision}{"\t"}{.spec.template.metadata.annotations.coomia\.com/release-inputs}{"\n"}'
kubectl -n "$CLASSIC_ENTERPRISE_NAMESPACE" get deployment classic-enterprise-api \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="api")].image}{"\n"}'
```

After rollback, rerun the isolated readiness and data-boundary checks. A
rollback is accepted only when the old image, configuration, credentials,
database schema, object prefixes, topics, and License state are all compatible.
The recorded template labels and immutable image reference must also match the
selected previous release; a healthy Pod alone does not prove a safe rollback.

## Evidence boundary

This document does not claim a deployment, rollback drill, domain cutover, or
business acceptance. Those remain CE-25 through CE-27 gates and require an
authorized cluster with recorded request, rollout, storage, and domain evidence.
